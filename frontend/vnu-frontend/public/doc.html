1. Kiến trúc Hệ thống & Luồng đi của Dữ liệu

Hệ thống tra cứu được xây dựng trên mô hình Kiến trúc 3 lớp (Three-Tier Architecture) mở rộng với Nginx Gateway ở cổng 80 để đáp ứng được cấu hình tường lửa nghiêm ngặt của mạng trường học (chỉ cho phép cổng 80 và 443 đi qua).

Biểu đồ Luồng dữ liệu qua Nginx Gateway

Giải thích chi tiết các thành phần:

  • Nginx (Reverse Proxy): Lắng nghe ở cổng 80. Khi người dùng truy cập địa chỉ IP của server, Nginx sẽ đứng ra làm trung tâm điều phối. Nếu yêu cầu bắt đầu bằng /api/v1/, Nginx sẽ định tuyến ngầm (forward) yêu cầu đó sang container FastAPI đang chạy ở cổng 8000. Mọi yêu cầu khác sẽ được trỏ sang container React chạy ở cổng 5173. Giải pháp này giúp loại bỏ lỗi CORS (vì cả Frontend và Backend đều chạy chung một Domain/IP).
  • FastAPI Backend: Tiếp nhận các yêu cầu nghiệp vụ qua API RESTful, thực hiện xác thực bảo mật qua token JWT, kiểm tra tính đúng đắn của dữ liệu đầu vào và truy vấn CSDL.
  • PostgreSQL & Redis: PostgreSQL đảm bảo lưu trữ toàn vẹn thông tin đề tài. Redis hỗ trợ lưu trữ cache tạm thời các từ khóa tìm kiếm phổ biến để phản hồi ngay lập tức dưới 10 miligiây và lưu token đăng xuất (Blacklist).

2. Luồng Logic Xử lý các Nghiệp vụ chính

A. Luồng xử lý Đăng nhập & Xác thực Admin (Authentication & Authorization)

Làm thế nào để hệ thống bảo vệ các thao tác Thêm, Sửa, Xóa đề tài?

Mật khẩu của người dùng được băm một chiều bằng thuật toán bcrypt trước khi lưu vào cơ sở dữ liệu. Khi admin thực hiện đăng nhập thành công, Backend sẽ tạo ra một chuỗi JWT Token được mã hóa kèm hạn dùng gửi về cho Frontend lưu trữ tại localStorage. Mỗi khi Admin thực hiện Thêm/Sửa/Xóa, Frontend sẽ đính kèm token này vào Header của HTTP Request. Backend sẽ dùng Middleware giải mã và kiểm tra quyền trước khi thao tác xuống DB.

B. Luồng xử lý Cập nhật & Đồng bộ dữ liệu Cache

Tại sao dữ liệu trên trang chủ luôn cập nhật tức thì khi Admin chỉnh sửa?

Để hệ thống đạt tốc độ tìm kiếm nhanh nhất, kết quả tìm kiếm được lưu đệm trên Redis. Tuy nhiên, khi Admin thực hiện thêm mới một đề tài hoặc cập nhật đề tài cũ, dữ liệu trên Redis sẽ bị cũ (stale). Do đó, Backend được thiết lập cơ chế **Invalidate Cache**: Ngay sau khi thực hiện `COMMIT` dữ liệu mới thành công vào PostgreSQL, hệ thống sẽ kích hoạt một **Background Task** để xóa toàn bộ các key cache liên quan trên Redis. Khi người dùng ngoài trang chủ thực hiện tìm kiếm lại, do không tìm thấy cache (Cache Miss), hệ thống sẽ truy vấn trực tiếp xuống Postgres và nạp dữ liệu mới nhất vào Redis.

3. Thuật toán Tìm kiếm Nâng cao (Hybrid Search Engine)

Hệ thống sử dụng mô hình tìm kiếm lai kết hợp giữa tìm kiếm toàn văn tiếng Việt không dấu (Full-Text Search) và đối sánh khoảng cách ký tự (Fuzzy Similarity) để khắc phục triệt để các hạn chế khi người dùng nhập từ khóa thiếu dấu hoặc viết sai lỗi chính tả.

1 Full-Text Search (TSVector & TSQuery)

Dữ liệu cột Tiêu đề và Tác giả được chuẩn hóa không dấu thông qua hàm bọc `public.immutable_unaccent` và lưu trữ dưới dạng vector từ tố `TSVECTOR`. CSDL sử dụng chỉ mục **GIN (Generalized Inverted Index)** để tìm kiếm nhanh chóng bằng cách tra cứu ngược từ khóa, rút ngắn thời gian tìm kiếm xuống hàng trăm lần so với phép quét bảng thông thường.

2 Fuzzy Search (pg_trgm Similarity)

Kích hoạt extension `pg_trgm` để phân tích văn bản thành các cụm 3 ký tự liên tiếp. Khi người dùng tìm kiếm, CSDL sẽ tính toán độ tương đồng giữa chuỗi nhập vào và văn bản gốc bằng hàm `similarity()`. Nếu độ tương đồng vượt ngưỡng tối thiểu (0.2), tài liệu sẽ được xếp vào kết quả gợi ý để phòng trường hợp gõ nhầm ký tự.

Công thức chấm điểm độ liên quan (Scoring Mechanism):

Total_Score = (ts_rank(search_vector, tsquery) * 2.0) + similarity(unaccent(title), unaccent(q))

* Trong đó: Hàm ts_rank tính toán tần suất xuất hiện của từ khóa, Tiêu đề được gán mức ưu tiên cao hơn tác giả. Điểm số tương đồng của pg_trgm được cộng thêm vào để xếp hạng tối ưu các đề tài có độ khớp tương đối. Kết quả cuối cùng được sắp xếp giảm dần theo Total_Score.

4. Thiết kế Hệ thống API RESTful (API Documentation)

Mọi tương tác giữa giao diện người dùng và máy chủ đều thông qua các API chuẩn hóa được bảo mật bằng Rate Limiting (giới hạn tần suất gọi tối đa 30 lượt/phút đối với tìm kiếm để tránh bị tấn công DDOS).

Phương thức Đường dẫn (Endpoint) Quyền truy cập Mô tả chức năng
GET /api/v1/projects/search Công khai (Public) Tìm kiếm & phân trang danh sách đề tài.
GET /api/v1/projects/{id} Công khai (Public) Lấy thông tin chi tiết một đề tài cụ thể.
POST /api/v1/projects Admin duy nhất Thêm một đề tài nghiên cứu khoa học mới.
PUT /api/v1/projects/{id} Admin duy nhất Chỉnh sửa thông tin đề tài đang có.
DELETE /api/v1/projects/{id} Admin duy nhất Xóa đề tài khỏi cơ sở dữ liệu.
GET /api/v1/filters Công khai (Public) Tự động kết xuất danh sách lọc động.

5. Thiết kế Cấu trúc Cơ sở dữ liệu (Database Design)

Cơ sở dữ liệu của dự án được chuẩn hóa mức cao, sử dụng kiểu dữ liệu tối ưu của PostgreSQL để tăng tốc truy vấn văn bản lớn.

Bảng Đề tài Nghiên cứu: `research_projects`

Tên Cột (Field) Kiểu Dữ liệu Ràng buộc (Constraints) Mô tả
id VARCHAR PRIMARY KEY, INDEX Chuỗi mã khóa duy nhất (UUID).
title VARCHAR(500) NOT NULL Tiêu đề đề tài nghiên cứu khoa học.
author VARCHAR(200) NOT NULL Chủ nhiệm đề tài.
target_audience VARCHAR NULLABLE Đối tượng áp dụng (Giảng viên / Sinh viên).
field VARCHAR NULLABLE Lĩnh vực khoa học thực hiện.
year INTEGER NULLABLE Năm thực hiện công trình.
status VARCHAR NULLABLE Trạng thái (Đang thực hiện, Đã nghiệm thu).
abstract TEXT NULLABLE Tóm tắt nội dung đề tài nghiên cứu.
keywords JSON DEFAULT '[]' Mảng chứa các từ khóa/tags dạng linh hoạt.
pdf_url VARCHAR NULLABLE Đường dẫn tài liệu hoặc file báo cáo PDF.
search_vector TSVECTOR COMPUTED, GIN INDEX Cột tự động sinh dữ liệu từ tố để tìm kiếm FTS.

6. Cấu trúc Tổ chức Mã nguồn (Codebase Directory Layout)

Cấu trúc mã nguồn của dự án được module hóa theo đúng nguyên lý phân tách mối quan tâm (Separation of Concerns) giúp các nhà phát triển khóa sau dễ dàng định vị các file cần thay đổi:

Backend Folder Layout

backend/app/
├── core/         # Cấu hình cài đặt, bảo mật JWT
├── db/           # Kết nối Database Session
├── models/       # Định nghĩa Cấu trúc Bảng CSDL
│   └── project.py
├── schemas/      # Định nghĩa Schema Validate (Pydantic)
│   └── project.py
├── api/v1/       # Luồng xử lý logic API chính
│   ├── auth.py
│   └── search.py
└── utils/        # Hàm phụ chuẩn hóa tiếng Việt

Frontend Folder Layout

frontend/vnu-frontend/src/app/
├── pages/        # Các màn hình chính
│   ├── HomePage.tsx
│   ├── AdminPage.tsx
│   └── ProjectDetailPage.tsx
├── layouts/      # Khung sườn Header, Footer
├── features/     # Component lớn theo tính năng
│   └── search/ (SearchBar, SearchFilters)
├── shared/       # Thẻ ProjectCard, Type định nghĩa
└── core/services/ # Kết nối gọi API HttpClient
