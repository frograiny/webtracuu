Chương 1. Tổng Quan & Bối Cảnh Dự Án

1 Bối cảnh thực tế

Trong kỷ nguyên số hóa, số lượng đề tài nghiên cứu khoa học (NCKH), luận văn, luận án và các bài báo khoa học tại các trường đại học ngày càng gia tăng theo cấp số nhân. Tuy nhiên, việc quản lý và tra cứu các tài liệu này hiện đang vấp phải nhiều rào cản nghiêm trọng:

❌ Các vấn đề của hệ thống cũ

  • Phân tán dữ liệu: Dữ liệu lưu trữ rải rác ở nhiều khoa, viện, không có kho lưu trữ tập trung (Centralized Repository).
  • Hạn chế tìm kiếm: Sử dụng LIKE '%keyword%' dẫn đến tốc độ O(N) — quét toàn bảng. Không nhận diện được lỗi gõ sai, thiếu dấu, từ đồng nghĩa.
  • Thiếu khả năng mở rộng: Kiến trúc Monolith không thể chịu tải lớn (High Traffic) trong mùa bảo vệ luận văn.
  • Bảo mật lỏng lẻo: Thiếu RBAC, Session Management chặt chẽ, dễ bị Brute-force hoặc DDoS.

2 Chiến lược Indexing

Để đảm bảo hiệu năng hàng triệu bản ghi, việc thiết kế Index là yếu tố sống còn.

Cột search_vector (Generated Column)

Bất cứ khi nào title, author, hoặc abstract được INSERT/UPDATE, PostgreSQL tự động tính toán lại cột này qua hàm phân tích từ vựng (Lexer/Stemmer) — loại bỏ Stopwords và đưa từ về gốc.

Loại IndexÁp dụngMục đích
B-Tree status, created_at Lọc dữ liệu nhanh (Equality & Range)
GIN search_vector Inverted Index cho FTS — giảm O(N) → O(log N)
GIN Trigram title (gin_trgm_ops) Fuzzy Search — tìm kiếm mờ khi gõ sai chính tả 
-- B-Tree Index
CREATE INDEX idx_projects_status ON projects(status);

-- GIN Index cho Full-Text Search
CREATE INDEX idx_projects_search ON projects USING GIN(search_vector);

-- Trigram Index cho Fuzzy Search
CREATE INDEX idx_projects_title_trgm ON projects USING GIN(title gin_trgm_ops);

Chương 5. Thiết Kế Chi Tiết Các Phân Hệ Cốt Lõi

1 Phân hệ Tra Cứu Nâng Cao (Search Engine)

Vấn đề: Câu lệnh LIKE '%...%' khiến DB bị thắt cổ chai (Bottleneck).
Giải pháp: Áp dụng luồng xử lý Search Engine ngay trong PostgreSQL.

🔍 Search Flow — Sequence Diagram
① User gửi: GET /search?q=Tri tue nhan tao
⬇️
② Normalizer: xóa khoảng trắng, lowercase, synonym rewrite → "ai"
⬇️
③ Kiểm tra Redis: GET search_cache:q:ai
⬇️
✅ Cache Hit
Trả kết quả ngay
Latency: ~2ms
❌ Cache Miss
Query FTS bằng GIN Index
Lưu kết quả vào Redis (TTL: 1h)
Latency: ~50ms

Thuật toán Xếp hạng (Ranking)

TrườngTrọng sốMức ưu tiên
TitleWeight ACao nhất
AuthorWeight BTrung bình
AbstractWeight CThấp

Kết quả sắp xếp theo hàm ts_rank() kết hợp setweight() của PostgreSQL.

2 Chiến Lược Bộ Đệm (Cache-Aside Pattern)

Bài toán Nhất quán dữ liệu (Data Consistency)

Nếu Admin sửa tiêu đề đề tài nhưng Redis vẫn lưu dữ liệu cũ → người dùng thấy thông tin sai.

Giải pháp: Event-driven Cache Invalidation

  1. Transaction commit thành công vào DB
  2. FastAPI đẩy Background Task
  3. Task dùng SCAN tìm tất cả keys search_cache:* → DEL
  4. Lần search tiếp → Cache Miss → DB trả dữ liệu mới → nạp lại cache

4 Phân hệ Vận hành & Giám sát (Observability)

📊 Prometheus Metrics

Tích hợp prometheus-fastapi-instrumentator tự động intercept mọi Request/Response:

  • HTTP_REQUESTS_TOTAL — Tổng số lượng request
  • HTTP_REQUEST_DURATION_SECONDS — Histogram đo Latency (P50, P95, P99)

📈 Grafana Business Analytics

  • Lưu lượng tìm kiếm theo thời gian thực
  • Từ khóa "Zero-result" → Admin thêm dữ liệu hoặc từ đồng nghĩa

🐳 Docker Auto-healing

Docker Daemon ping /health mỗi 30s. Nếu fail 3 lần liên tiếp → tự động KILL & RESTART container → đảm bảo High Availability.
